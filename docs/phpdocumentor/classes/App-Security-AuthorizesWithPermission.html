AuthorizesWithPermission

AuthorizesWithPermission.php : 48

Gives a use case the two halves of owning its permission: declaring it at boot and enforcing it per call.

A permission belongs to exactly one use case, so the use case is the only sensible place to name it. declarePermission() runs from the constructor at WorkerStart — the "logo na criação" moment — and keeps only the slug; authorize() is the first line of execute().

The 403 is produced here, as a plain failed Result. The API layer never decides it, it only maps LeafContext->code onto the response.

Not every use case uses this trait: the unguarded ones — login, session validation, setup — have no permission to declare, because there is no caller yet to check one against.

authorize()

AuthorizesWithPermission.php : 110

Guards the use case. Returns a successful void {@see Result} when the caller may proceed, or the 403 failure to hand straight back:

private authorize(UserContext $context) : Result<string|int, null> 
$authorized = $this->authorize($command->context);
if (!$authorized->isSuccess()) {
    return Result::failure($authorized->getErrorId());
}

The message is deliberately the same whoever is refused and whatever they were refused: telling a caller which permission they lack describes the shape of the system to someone who has just been told they may not see it.

declarePermission()

AuthorizesWithPermission.php : 82

Declares this use case's permission and returns its slug, to be assigned straight to {@see $permission} in the constructor:

private declarePermission(IRegisterPermissionUseCase $registrar, string $slug) : string 
$this->permission = $this->declarePermission($registrar, 'product:create');

It returns rather than assigns because a readonly property may only be written in the declaring class's constructor — an assignment made inside this method would be rejected.

The slug is all a permission is: see IPermission for why it carries no label or description.
