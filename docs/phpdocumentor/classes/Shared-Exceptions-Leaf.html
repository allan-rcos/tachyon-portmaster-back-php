Leaf.php : 37

The registry a failed {@see Result}'s error id points into.

A Result carries an int rather than the error itself, which is what lets a failure be typed Result<never> and propagate through any signature. This holds the LeafContext that int resolves to.

Storage is per coroutine while a request is being served, so concurrent requests cannot read each other's errors and the entries are freed with the coroutine. Errors raised where no coroutine exists fall back to a bounded process-wide store — see $processErrors.

$processErrors

Leaf.php : 58

Fallback store for errors raised **outside** a coroutine.

private static array<int, LeafContext> $processErrors = []

The coroutine context is the right home during a request: it isolates concurrent requests and is freed with them. But errors also occur where no coroutine exists — the composition root at WorkerStart, CLI entry points, and unit tests — and there the context write is silently dropped, leaving getError() to return null and the caller to report "unknown error". This keeps those recoverable.
